# 低代码平台契约（P0）

更新于 2026-10-30。本目录是低代码平台的**实现契约**，代码以此为准；实现与文档冲突时，先改文档再改代码。

## 定位

表单驱动型低代码，私有部署，服务内部业务。对标明道云 / 简道云这一类，**不是**画布式页面搭建器（Retool / Appsmith）。

- **平台负责**：表结构、字段、索引、列表与表单、权限、数据范围、发布与版本。
- **代码负责**：任何有业务规则的操作、跨系统调用、事务边界，以 handler 形式注册。
- **平台永不负责**：任意 SQL、表达式引擎、脚本、前端动态加载组件。

## 三条边界

1. **平台管结构，代码管行为。** 标准 CRUD 走平台，业务动作写 handler。
2. **平台拥有的数据自己建表，别人的数据只读接入。** 外部数据源只做查询，不建表、不回写。
3. **不追求零代码。** 目标是让"新建一个列表 / 表单页面"从写八个文件变成配一个实体 + 写一个 handler。

## 关键决策

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 存储 | 每实体一张物理表 | 要被报表、BI 和其他系统直接读，JSON 存储撑不住 |
| schema | **不写进模型，由连接账号决定**：生产用 `ZX_LOWCODE` 账号，迁移里不带 schema 前缀 | EF 迁移会把 schema 烤进 SQL，写死就没法在别的 schema 复用同一份迁移 |
| 表命名 | `LC_{APP}_{ENTITY}` | 一眼区分平台表与业务表 |
| **数据访问** | **元数据走 EF Core，业务表走 Dapper + 手写 SQL** | 业务表的列是运行时才有的，EF 的编译期模型用不上；共用同一连接与事务 |
| DDL | 测试环境自动执行，生产导出交 DBA | 生产通常不给应用账号 `CREATE TABLE` |
| DDL 产物 | 单一 `SchemaChange`，SQL 只是它的渲染 | 避免测试与生产两条代码路径 |
| 元数据迁移 | 独立 DbContext + 独立迁移历史表 | 低代码可整体撤除，不动 Identity 的迁移历史 |
| 模块形态 | `Services/LowCode/*` 五个项目，同进程宿主 | 现在拆服务只有成本没有收益 |
| **设计器形态** | **字段列表 + 拖拽排序 + 分栏容器 + 实时预览，不做自由定位画布** | 表单类场景流式布局足够；自由坐标会毁掉响应式与导出 |
| **主从** | **第一期松主从（外键关联），第二期紧主从（嵌入式子表）** | 紧主从成本约为松主从的 3 倍 |
| **导出** | **服务端 MiniExcel，不做前端导出** | 导出要全量 + 权限 + 审计，前端只拿得到当前页 |
| 权限 | 复用 `PERMISSION` / `MENU`，新增 `SOURCE` / `OWNER_CODE` | 角色授权与菜单树零改动 |
| 数据范围 | `scopeMode: none / column`，按 SBU 过滤 | 复用 `[RequireSbu]` 与 `CurrentSbuContext` |
| 版本 | 草稿 + 已发布快照 + 历史版本 | 发布不影响线上，可回滚 |
| 退役 | 停用 → 归档 → 清理，默认不物理删 | 一个实体牵连七类对象 |

**使用者是开发 / 实施顾问，不是业务人员。** 这条决定了字段类型可以放开、编辑器可以偏专业，也决定了"手写 JSON 配一个实体"是可接受的中间态。

## 设计器形态

设计器是产品本体，但**不是画布**。三种形态成本差十倍，只做第二档：

| 形态 | 用户能做什么 | 结论 |
| --- | --- | --- |
| 自由定位画布 | 任意坐标摆放 | ❌ 不做。会毁掉响应式、打印、导出；表单类场景用户会排乱 |
| **拖拽排序 + 分栏** | 拖动字段顺序、拖进分组、2/3 列分栏 | ✅ **做这个** |
| 纯列表配置 | 只能上下移 | ❌ 太弱 |

五个面板，一个模型：

| 面板 | 设计什么 |
| --- | --- |
| 字段 | 名称、类型、必填、唯一、默认值、选项、顺序 |
| 视图 | 列、宽度、筛选、排序、分页 |
| 操作 | 有哪些按钮，各要什么权限 |
| 关联 | 字段关联到哪个实体或外部数据集 |
| 页面 | 把视图和表单组合成菜单入口 |

两条硬规则：

1. **设计器产出的 JSON 就是运行时读的那份**，中间没有转换层。
2. **预览直接跑运行时渲染器**，不写第二套"设计器预览组件"。

## 第一个落地场景

`mes.material_usage`——MES 机种用料盘点。选它是因为它同时压到平台的六个能力：外部只读数据集、主从、行内编辑、导出、权限、SBU 范围。

| 能力 | 这个场景怎么用 |
| --- | --- |
| 外部只读数据集 | 机种 / 线体 / 站点 / 料号来自 MES 视图，只读，带 SBU 参数 |
| 主从 | 盘点单（主）+ 用料明细（子），第一期用松主从 |
| 行内编辑 | 明细里直接改用量，不弹窗 |
| 导出 | 服务端导出 Excel，按当前筛选条件全量 |
| 权限 | `mes.material_usage.*` 五个码 |
| SBU | 盘点单按 `SBU_ID` 隔离 |

详见 [pilot-material-usage.md](pilot-material-usage.md)。

## 术语

| 术语 | 含义 |
| --- | --- |
| 应用 Application | 业务模块容器，权限与发布的边界 |
| 实体 Entity | 一张物理表 + 一组字段 |
| 视图 View | 实体的一个列表视图（列、筛选、排序） |
| 页面 Page | 应用内可访问的入口，由若干区块组成 |
| 数据集 Dataset | 外部只读数据源的字段投影 |
| SchemaChange | 一次结构变更（建表、加列、加索引） |
| 退役 Decommission | 停用 → 归档 → 清理的完整下线流程 |

## 明确不做

通用 CRUD 生成器、表达式引擎、任意 SQL 输入、前端按配置动态 `import` 组件、跨数据集事务、低代码直连 MES 表。这些不是"以后再补"，是**设计上不做**——一旦开口，平台会变成第二套框架。
