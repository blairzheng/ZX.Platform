# 成员业务文档编写规范

[返回首页](../README.md) · [业务文档目录](business/README.md)

本文说明成员完成业务开发后应维护哪些文档，以及如何写清当前功能。前后端仓库采用相同目录约定，分别维护自己负责的内容；共性编写约定调整时，同步两边的本文件。

## 1. 文档放在哪里

具体模块的文档统一放在 `docs/business/`，按业务领域分组，文件名使用稳定的英文小写名称。现有一键盘点作为参考：

```text
docs/
  03-documentation.md             成员编写规范（本文件）
  business/
    README.md                     业务文档索引
    inventory/
      stocktake.md                一键盘点
```

每个模块先维护一份文档；内容明显变长时，再按实际需要拆成操作说明、接口契约等，并保留模块入口链接。前后端对应模块尽量使用相同相对路径，便于协作。

`docs/business/` 只收录具体业务说明和索引。开发规范、配置与启动、发布说明等系统级文档维持现有位置，由对应负责人按平台变更维护；普通业务交付不要求逐份修改这些文档。本文也是系统级的编写规范，放在 `docs/` 下。

## 2. 每次完成业务后更新什么

| 本次改动                                               | 要维护的文档                                                     |
| ------------------------------------------------------ | ---------------------------------------------------------------- |
| 新增一个已实现的业务模块                               | 新建对应业务文档，并在 `docs/business/README.md` 增加入口        |
| 修改操作流程、字段、校验、查询筛选、计算口径或状态规则 | 更新对应业务文档受影响的段落                                     |
| 修改权限、SBU 范围、分页、导出或数据可见范围           | 更新对应业务文档的权限与范围说明                                 |
| 新增、调整或取消 AI 业务查询                           | 在该业务文档记录开放情况、可查询范围及限制；无需手抄动态查询目录 |
| 重命名、移动或下线模块                                 | 更新业务索引、引用链接，并说明当前可用状态                       |
| 仅调整内部实现，业务行为和契约均未变化                 | 无需为了提交新建文档；在提交说明中说明文档无变化的原因           |

业务文档与代码在同一次合并请求中交付。未完成的功能标明“待实现”，未执行的验证标明“未验证”，不能以文档代替功能实现或验收。

平台 AI 工具、源码资料机制或团队通用约定发生变化时，再按任务授权更新原有 AI 系统文档、`AGENTS.md` 或业务 Skill。每增加一个模块无需复制 Skill，也无需重复修改通用规则。

## 3. 前后端分别写什么

| 内容           | 前端仓库负责                                     | 后端仓库负责                                    |
| -------------- | ------------------------------------------------ | ----------------------------------------------- |
| 功能入口与操作 | 页面名称、组件标识、操作步骤、按钮显示条件       | 支持的业务动作及必要前置条件                    |
| 字段           | 界面名称、显示格式、输入校验、空状态             | 请求与返回字段、必填与可空、枚举、时间及单位    |
| 查询与结果     | 本地或服务端筛选、刷新、分页、图表、导出范围     | 接口方法与路径、参数、排序、分页及总数语义      |
| 权限与数据范围 | 页面/按钮需要的权限，以及实际使用的 SBU 请求配置 | 原接口权限、已校验 SBU 范围、记录归属与其他限制 |
| 业务规则       | 页面实际采用的展示和计算口径                     | 服务端规则、状态流转、计算与数据来源            |
| AI 查询        | 用户入口与本模块相关的使用限制                   | 是否加 `[AiQuery]`、只读边界、完整性与查询范围  |

后端接口契约以后端文档和实际代码为依据，前端说明页面实际采用的行为。跨仓库内容写明仓库名及相对文档路径，避免使用个人电脑的绝对路径；只维护必要的摘要，详细内容引用对应仓库，不把整份接口文档复制到两边。

## 4. 一份业务文档怎样组织

先讲清功能和业务规则，再列必要的开发依据。下面的结构可直接用于新增模块，按实际功能删减或合并章节，不必给没有的功能留空壳：

```markdown
# 模块名称

## 功能与当前范围

解决什么问题，已经支持哪些能力，哪些尚未支持。

## 入口与使用流程

前端写页面入口与操作步骤；后端写业务动作或调用前提。

## 字段、查询与业务规则

字段含义、筛选方式、计算口径、分页或完整结果、状态规则。

## 权限、数据范围与 AI 查询

需要的权限、SBU 归属、AI 是否开放及实际限制。

## 限制与验证情况

已知限制，已验证及未验证的内容；有问题时的已确认处理方式。

## 开发依据

相关页面、API、DTO、Service、仓储等源码的相对链接。
```

写作时注意：

- 使用当前页面名称和真实字段含义；不确定的单位、空值或计算规则先核实，不编造示例数据、固定菜单路径或尚不存在的接口。
- 明确全量、分页和筛选后的结果区别；当前页不能写成全部，空值不能默认当零。数量、金额、卷数等单位分别说明。
- 将“当前已实现”“后续计划”“环境中已配置”分开；有源码不等于目标环境菜单已配置、权限已授权或迁移已执行。
- 只列影响使用与协作的字段和规则，长实现细节通过源码链接定位；业务规则变更直接维护对应段落，不把文档堆成每次提交的流水账。
- 不记录真实账号密码、模型 Key、Token、连接字符串或生产数据明细。使用说明需要示例时，采用明确的虚构业务值。
- 验证结果如实记录日期、范围和结果；只静态阅读时直接说明，不能写成接口联调或浏览器验收通过。文档更新不改变仓库对测试、运行和环境操作的授权约定。

## 5. 提交前核对

1. 对照本次差异，确认受影响的操作、字段、规则、权限和范围已同步到业务文档。
2. 新增或移动文档后，更新业务索引并检查相对链接；同一业务的前后端说明应一致。
3. 在提交或合并请求说明中列出变更、验证结果、未验证事项及需要协作的菜单、权限、配置或迁移；文档无变化时说明原因。
