## 认证与跨服务授权

Identity 负责身份、厂区归属、角色和授权数据；`UserFactory` 表示厂区关系，不能替代功能权限。各业务服务定义并检查自己的权限代码，例如 `mes.orders.read`，并检查工单归属等业务规则。

已实现 JWT Access Token + 随机 Refresh Token：标准 JwtBearer 校验 JWT，随后检查 Redis 单账号会话和当前 `jti`，支持确认接管、强制下线；禁用、删除或自助改密码尝试撤销会话。明确接受数据库与 Redis 之间的并发窗口，不使用用户锁，竞态 Access 最长存活一个 Access 周期。新增受保护服务时仍需提取公共 JWT / Redis 认证组件，不逐请求 HTTP 调用 Identity。具体边界见[登录与会话](authentication.md)。Identity 已按角色功能权限授权，配置名单仅首次引导内置管理员，见[角色与权限](authorization.md)。

Gateway 可以做入口校验，但各业务服务仍要独立认证并检查授权，不能只依赖“请求来自 Gateway”。前端传入的 FactoryId 只是用户选择，服务端需要核实当前登录用户有访问权。Identity 已使用共享 Redis 权限缓存与版本失效，故障返回 503；跨服务权限目录与公共组件仍需设计，不把会话有效性等同于功能权限。

## 菜单名称多语言

2026-10-16 讨论后决定暂缓调整。当前菜单名称仍使用 `Title`（中文）与 `TitleEn`（英文），数据库、接口及前端保持现有实现。

后续增加越南文等语言时，改为菜单翻译表，不再按语言增加 `TITLE_VI` 等列。规划如下：

- 菜单主表保存层级、路径、组件、图标和排序等配置；翻译表保存 `MenuId`、`Language`、`Title`，以 `MenuId + Language` 保证唯一。
- 语言标识使用 `zh-CN`、`en-US`、`vi-VN` 等；迁移时将现有 `TITLE` / `TITLE_EN` 的内容分别保留为对应语言的翻译记录，并同步调整默认菜单初始化。
- 菜单编辑界面按系统支持的语言维护名称；导航、角色授权树及其他菜单名称展示统一按当前语言取值，缺失翻译时回退到默认语言。
- 前后端 DTO、菜单编辑及展示逻辑同步调整；页面上的“保存”“取消”等固定文案继续使用前端 i18n，后台维护的动态菜单名称由数据库翻译表管理。

该项仅记录后续方向，尚未创建翻译表或修改现有接口；实施时再确定具体表名、默认语言及接口契约。

## 厂区与多租户

厂区是当前业务关系的一部分；它是否完全等价于租户尚未确定。可能的业务环境包括一个厂区一个数据库，或多个厂区共库。

若后续需要动态切库，需要明确厂区到连接配置的映射、请求上下文、连接选择、跨厂区查询及跨库事务边界。当前 FactoryId 筛选只是用户管理的查询条件，不提供这些能力。

## 事务、幂等与 Redis

事务保证一次保存中的多条变更一起提交；幂等保证同一个业务操作重复请求只产生一次业务效果；限流限制请求频率。三者不能相互替代。

Identity 创建用户有天然唯一键 `NormalizedAccount`，当前允许重复提交返回 `409`，依靠数据库唯一索引防止重复记录。暂不为它创建通用幂等表或使用 Redis 做提交幂等；现有 Redis 用于会话与权限缓存。需要“相同请求返回第一次 UserId”时，再增加结果存储。

前端 loading 减少重复点击，写请求不无条件自动重试；发生网络错误或超时时先查询已保存结果。客户端失败不等于数据库没有提交。

### MES 报工方向

MES 累加型操作需要稳定 RequestId。例如同一次报工 2 小时不应因重试被累计成 4 小时。

```text
开始一次报工 → 生成稳定 RequestId
→ 双击 / 超时重试沿用同一个 RequestId
→ 后端查已有记录，有则返回第一次结果
→ 无记录则在同一数据库事务中保存报工与 RequestId
→ 唯一冲突时查询并返回已有结果
```

RequestId 建立数据库唯一索引；相同 RequestId 携带不同业务内容应拒绝，不能覆盖第一次结果。如果一次操作只创建主记录，可把 RequestId 放在报工表；需要多个状态和结果时，再建立有业务含义的提交记录。

Redis 一次性 Token 被消费后，业务失败或响应丢失无法自然恢复第一次结果；Redis 与业务库也不在同一事务。Redis 可用于减少竞争或缓存，但数据库约束及业务结果记录仍是正确性的基础。

若事务外还有外部系统、设备或不可撤回消息，需要进一步设计 Outbox、消费幂等和补偿。MES 服务与上述流程当前都尚未实现。

## 服务与数据库演进

当前后端同仓管理服务，不意味着所有模块立即独立部署。以明确业务边界、数据所有权和扩缩容需求为依据新增服务；不把每张表拆成微服务。

开发阶段可在同一 SQL Server 实例建立各服务自己的数据库。跨服务通信选 HTTP、gRPC 或消息时，需要结合实际用例确定；当前没有服务发现、消息总线或跨服务事务框架。

数据库集群、分片和高可用解决不同的容量 / 吞吐 / 可用性问题，不能通过业务代码随意复制数据替代。先观察索引、SQL、分页、数据生命周期和负载，再选择数据库产品的成熟方案。早期 Oracle / RAC 等讨论保留在[历史记录](history/development-notes.md)。

## 限流与容量

Identity 已按 IP + 方法 + 路由模板做单实例频率限制。总并发上限和统一后端超时尚未加入，报表和下载不能由普通接口的假定耗时决定。

多个实例各自计数。同一出口 IP 下用户会共享额度；认证接入后可评估按用户标识分组。需要严格集群总额度时，再设计入口或分布式计数。容量、额度和是否增加并发控制应依据真实服务器、数据库和业务压测结果。

## 接口性能与启动预热

2026-10-13 本地调试时，重启后首次厂区列表请求约 2.75 秒，后续约 64 毫秒；用户列表等请求观察到约 20～130 毫秒的波动。这些是开发环境的少量观察，不能作为生产性能基准。首次请求可能包含 JIT 编译、EF Core 模型与查询初始化、数据库连接等开销，具体占比尚未测量。

后期评估轻量接口能否达到 20～30 毫秒的后端处理耗时，不承诺每次请求都在此范围内。浏览器 Network 的总耗时还包含网络、排队、Gateway 转发和响应接收，应与后端处理、SQL 执行耗时分别记录。

部署阶段再开展以下工作：

1. 使用 Release 构建，不挂调试器，按预计数据量、并发量和真实网络环境测量。
2. 分别记录重启后的首次请求与预热后的请求耗时，统计 P50 / P95 / P99（分别有 50% / 95% / 99% 的请求耗时不超过该值），按接口确定目标。
3. 对持续较慢的接口，区分网络与 Gateway、后端处理和数据库耗时，再根据测量结果调整 SQL、索引或代码。
4. 如果首次请求仍明显慢，再实现启动预热：服务启动后执行有代表性的只读查询，预热成功后才标记准备就绪并接收用户流量。预热不得调用新增、修改或删除接口；只预热实际执行到的路径，不能保证所有接口首次调用都已初始化。

当前先推进业务功能，性能测量、优化与启动预热留到部署阶段评估。

## 日志与追溯

2026-10-17 当前先实现运行与接口日志：沿用 `ILogger`，Gateway 和 Identity 使用框架 HTTP Logging 输出方法、路径、状态码及耗时，scope 带 TraceId；异常处理器继续记录业务 / 领域警告、唯一冲突和系统错误。Console Provider 后台队列输出，满载丢弃新日志；开发用文本，生产用 JSON，Linux systemd 部署交给 journald 收集，配置与部署验收见[运行与接口日志](logging.md)。

暂不接入 MQ、独立审计服务、Loki、Prometheus 或平台日志页面。后续再设计跨服务共用的登录 / 操作审计能力：业务服务产生事件，统一保存查询；可靠投递、保留期限和是否独立部署届时确定。业务字段前后值、原因与版本也属于后续审计历史。

密码、Token 和连接字符串不写日志。MES 关键追溯需要历史表、版本或业务事件，不能只靠普通文本日志。已提交数据的撤销需要业务补偿或版本机制，应用版本回滚也不会自动回滚数据库和业务数据。
