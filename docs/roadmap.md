## 认证与跨服务授权

Identity 负责身份、厂区归属、角色和授权数据；`UserFactory` 表示厂区关系，不能替代功能权限。各业务服务定义并检查自己的权限代码，例如 `mes.orders.read`，并检查工单归属等业务规则。

后续由 Identity 签发 Token。Gateway 可以做入口校验，但各业务服务仍要独立验证 Token 和授权，不能只依赖“请求来自 Gateway”。前端传入的 FactoryId 只是用户选择，服务端需要核实当前登录用户有访问权。

初期候选方案是业务服务向 Identity 查询权限并短时缓存；具体服务间认证、缓存失效、权限变更传播及不可用时行为尚未定稿。权限放入 Token 或事件同步方案等需求明确后再决定。

## 厂区与多租户

厂区是当前业务关系的一部分；它是否完全等价于租户尚未确定。可能的业务环境包括一个厂区一个数据库，或多个厂区共库。

若后续需要动态切库，需要明确厂区到连接配置的映射、请求上下文、连接选择、跨厂区查询及跨库事务边界。当前 FactoryId 筛选只是用户管理的查询条件，不提供这些能力。

## 事务、幂等与 Redis

事务保证一次保存中的多条变更一起提交；幂等保证同一个业务操作重复请求只产生一次业务效果；限流限制请求频率。三者不能相互替代。

Identity 创建用户有天然唯一键 `NormalizedAccount`，当前允许重复提交返回 `409`，依靠数据库唯一索引防止重复记录。暂不为它创建通用幂等表或引入 Redis。需要“相同请求返回第一次 UserId”时，再增加结果存储。

前端 loading 减少重复点击，写请求不无条件自动重试；发生网络错误或超时时先查询已保存结果。客户端失败不等于数据库没有提交。

### MES 报工方向

MES 累加型操作需要稳定 RequestId。例如同一次报工 2 小时不应因重试被累计成 4 小时。

```text
开始一次报工 → 生成稳定 RequestId
→ 双击 / 超时重试沿用同一个 RequestId
→ 后端查已有记录，有则返回第一次结果
→ 无记录则在同一数据库事务中保存报工与 RequestId
→ 唯一冲突时查询并返回已有结果
```

RequestId 建立数据库唯一索引；相同 RequestId 携带不同业务内容应拒绝，不能覆盖第一次结果。如果一次操作只创建主记录，可把 RequestId 放在报工表；需要多个状态和结果时，再建立有业务含义的提交记录。

Redis 一次性 Token 被消费后，业务失败或响应丢失无法自然恢复第一次结果；Redis 与业务库也不在同一事务。Redis 可用于减少竞争或缓存，但数据库约束及业务结果记录仍是正确性的基础。

若事务外还有外部系统、设备或不可撤回消息，需要进一步设计 Outbox、消费幂等和补偿。MES 服务与上述流程当前都尚未实现。

## 服务与数据库演进

当前后端同仓管理服务，不意味着所有模块立即独立部署。以明确业务边界、数据所有权和扩缩容需求为依据新增服务；不把每张表拆成微服务。

开发阶段可在同一 SQL Server 实例建立各服务自己的数据库。跨服务通信选 HTTP、gRPC 或消息时，需要结合实际用例确定；当前没有服务发现、消息总线或跨服务事务框架。

数据库集群、分片和高可用解决不同的容量 / 吞吐 / 可用性问题，不能通过业务代码随意复制数据替代。先观察索引、SQL、分页、数据生命周期和负载，再选择数据库产品的成熟方案。早期 Oracle / RAC 等讨论保留在[历史记录](history/development-notes.md)。

## 限流与容量

Identity 已按 IP + 方法 + 路由模板做单实例频率限制。总并发上限和统一后端超时尚未加入，报表和下载不能由普通接口的假定耗时决定。

多个实例各自计数。同一出口 IP 下用户会共享额度；认证接入后可评估按用户标识分组。需要严格集群总额度时，再设计入口或分布式计数。容量、额度和是否增加并发控制应依据真实服务器、数据库和业务压测结果。

## 日志与追溯

当前使用框架日志和异常处理器记录业务 / 领域警告、唯一冲突和系统错误，traceId 可用于关联。后续分别设计：

- 应用日志：运行、异常与性能。
- 访问日志：请求、状态码与耗时。
- 操作日志：谁执行了什么操作。
- 审计历史：业务字段前后值、原因与版本。

密码、Token 和连接字符串不写日志。MES 关键追溯需要历史表、版本或业务事件，不能只靠普通文本日志。已提交数据的撤销需要业务补偿或版本机制，应用版本回滚也不会自动回滚数据库和业务数据。
